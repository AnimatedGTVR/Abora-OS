# Abora OS v5.0 planning draft

This document records the early direction for Abora OS v5.0. It is intentionally a draft: details may change
as the design is discussed and tested.

## Release purpose

v5.0 is Abora's stability and credibility release: the release meant to show that Abora can be a safe, clean,
dependable alternative way to use NixOS. It is also intended to become the foundation that later Abora releases
build on without another broad rewrite.

Unlike earlier releases with short development cycles, v5.0 will have a longer stabilization period. The current
target window is **May-June 2027**, but release gates decide when it ships. The target moves if a use-case-blocking
bug remains.

The intended cadence after v5.0 is:

- one LTS foundation release each year;
- one mid-cycle feature release, such as v5.5, around November; and
- patch releases whenever security or serious reliability fixes are needed.

## Stability promise

"Stable" does not mean that no bug can ever exist. It means v5.0 should ship with no known bug that prevents a
supported use case such as installing, booting, logging in, updating, installing applications, recovering from a
failed change, or playing supported games.

The previous LTS must be able to update to the newest LTS. Updates must be transactional and recoverable, with a
working rollback path when an update fails.

## Architecture

v5.0 continues the "Shell as glue, not as the application" direction:

- **Rust** owns privileged or destructive system changes.
- **Zig** is proposed for small low-level observation tools, starting with a shared hardware/system probe.
- **Go** owns networked, diagnostic, CLI and TUI applications.
- **Nix** owns system configuration.
- **Shell** remains for compatibility wrappers, launchers and short system glue.
- Existing graphical applications may remain in their current languages while they are maintained.

Ports happen one piece at a time. Old and new implementations must be run against the same normal and hostile
inputs and shown to produce equivalent results before the old implementation is removed. Compatibility paths
required by older updaters remain as thin wrappers.

## Packages and applications

`grab` is the application/package frontend. It searches and manages packages from exactly two providers:

- Nixpkgs
- Flatpak/Flathub

`grab` should not contain a private application catalog, hard-coded recommendations, or silently substitute one
provider for another. When both providers match, interactive use should ask and non-interactive use should require
an explicit provider.

ANIX should not duplicate an imperative package installer. Its responsibility is system configuration, updates,
transactions, generations and recovery. Existing `anix package` behavior needs a documented compatibility and
migration plan before removal.

Release testing must cover representative real applications, including Steam, Doom through Steam, Zen Browser,
and packages from both supported providers.

## Desktop scope

The exact final support tiers remain open. MangoWM and River remain in scope. A custom-desktop path must let users
install a desktop maintained outside the built-in profile set without making it an officially supported profile.

PancakeDM is also in scope; its final role and requirements are still to be specified.

Abora Server is a separate project built from an Abora LTS foundation. Its proposed graphical profiles are limited
to:

- COSMIC
- GNOME
- KDE Plasma
- XFCE
- LXQt

It also supports headless installation and the custom-desktop path.

## Release candidates

Plan for at least five release candidates, adding more whenever a release-blocking fix needs validation:

1. **RC1: feature complete.** Feature freeze begins; exercise the installer, updater, ANIX, `grab`, desktops,
   PancakeDM, rollback and custom-desktop path.
2. **RC2: hardware and compatibility.** Test AMD, Intel and NVIDIA systems, UEFI and BIOS, laptops, networking,
   audio, suspend, gaming and previous-LTS upgrades.
3. **RC3: stress and recovery.** Test interrupted updates, damaged downloads, full disks, lost networking, failed
   services, repeated rebuilds and long-running workloads.
4. **RC4: release rehearsal.** Produce and test the exact public ISO, checksums, signatures, release metadata,
   clean installations, upgrades and documentation through the real release pipeline.
5. **RC5: final candidate.** Accept release-blocking fixes only, followed by a quiet testing period.

v5.0 requires two consecutive release candidates with no known critical or supported-use-case-blocking regression.
A severe fix resets the quiet period and normally produces another RC.

## Initial release gates

Before final release:

- clean installation and boot work on UEFI and Legacy BIOS;
- AMD, Intel and NVIDIA hardware receive real-hardware coverage;
- the previous LTS updates to v5.0 without manual repair;
- failed updates roll back to a bootable generation;
- every officially supported desktop installs and reaches a usable session at least once during the RC cycle;
- at least half of the supported desktops pass on each RC;
- Steam installs and Doom runs correctly;
- Zen Browser and representative Nixpkgs and Flatpak packages install, update and uninstall through `grab`;
- a custom desktop can be installed without modifying the installer itself;
- network loss, disk-full conditions, damaged downloads and interrupted operations produce safe, understandable
  failures;
- release artifacts, checksums and signatures are verified from their public download location; and
- no known critical or supported-use-case-blocking defect remains.

## Abora Server follow-up

Abora Server is not another v5.0 edition. It is a separate LTS-oriented project derived from the tested v5.0
foundation, and its support lasts until the next Server LTS (for example, a later v5.5 or v6.0 foundation).

Server validation should include headless installation, LTS-to-LTS upgrades, service recovery, resource pressure
and long-running AI workloads such as Ollama. The exact support period, workload matrix and release date remain TBD.

## Open decisions

- final built-in desktop list and support tiers;
- PancakeDM's exact role and fallback behavior;
- whether the public channels remain `stable` and `edge` or change names;
- the exact v5.0 feature-freeze and RC dates inside the May-June 2027 window;
- minimum supported hardware and storage requirements;
- the compatibility period for legacy ANIX package commands;
- the first Zig component and its stable output/interface; and
- which features are removed or deferred to v5.5.
