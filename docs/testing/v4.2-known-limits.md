# v4.2 known-limits validation

Run these checks on a disposable VM built from the release-candidate commit. They are runtime gates: passing
`make check` or Nix evaluation does not count as a pass. Record the ISO name, commit, firmware mode and result
in `docs/next-release-plan.md`.

## v4.1 update and removed initrd options

The current nixpkgs removed `boot.initrd.systemd.enable` and `boot.initrd.verbose`. v4.2 no longer sets them,
but that only proves evaluation. The installed system must boot with the new initrd.

1. Install the published v4.1 ISO in a disposable VM and boot it once.
2. Save the old generation and boot details:

   ```sh
   readlink -f /run/current-system
   uname -r
   sudo nix-env --list-generations --profile /nix/var/nix/profiles/system
   ```

3. Run the one-time 4.1 upgrade command from the release notes. The v4.1 updater otherwise picks its own
   `abora-update` wrapper as the resolver and stops safely; the variable selects the C# resolver v4.1 ships.
   A saved `unstable` channel resolves to `edge`:

   ```sh
   sudo env ABORA_UPDATE_RESOLVER_BIN=abora-update-resolver abora update
   ```

   It must pass checkout validation (4.2 keeps every path the v4.1 updater requires, see
   `scripts/release/legacy-required-paths.txt`) and print `Restarting with the synced updater.`
4. Let the 4.2 updater finish the build and switch.
5. Confirm the update completes, `/etc/nixos/abora/installed-base.nix` contains neither removed option, and a
   new system generation exists.
6. Reboot normally. Confirm `readlink -f /run/current-system` names the new generation, the kernel matches that
   generation, the login screen appears, and `systemctl --failed` has no newly failed unit.
7. Reboot once more and select the previous generation from the boot menu. Confirm it still boots.

If the candidate update fails before its updater is installed, preserve `/tmp/abora-update-*.log`, the saved
channel, the selected Git ref and `/etc/nixos/flake.{nix,lock}`. Fix the cause in 4.2 itself; there is
no v4.1 hotfix release.

## Reproduce the 4.0 hash-mismatch class

The original 4.0 report did not include the failing path and hashes, so its exact cause cannot be claimed as
reproduced. This injection recreates the damaged-store-path class safely and deterministically. It must be run
inside a disposable live VM, never on a host store worth keeping.

The published v4.0.1 ISO was also tested directly on 2026-10-31. It did not produce a hash mismatch: its
unlocked target evaluation followed current nixpkgs and failed because scripted initrd support, including
`boot.initrd.systemd.enable = false` and `boot.initrd.verbose`, had been removed. Keep that historical-source
drift failure separate from the still-unproven hash-mismatch report.

1. Boot the v4.2 release-candidate ISO and open a root terminal before partitioning.
2. Pick a regular file from a non-critical store path and make a writable copy of that whole path:

   ```sh
   victim_path="$(nix-store -qR /run/current-system | tail -n 1)"
   test -d "$victim_path"
   work_dir="$(mktemp -d /tmp/abora-corrupt.XXXXXX)"
   cp -a "$victim_path" "$work_dir/victim"
   victim_file="$(find "$work_dir/victim" -type f -size +0c -print -quit)"
   test -n "$victim_file"
   printf '\000' | dd of="$victim_file" bs=1 seek=0 count=1 conv=notrunc
   mount --bind "$work_dir/victim" "$victim_path"
   ```

3. Confirm the injection before opening the installer:

   ```sh
   nix-store --verify-path "$victim_path"
   ```

   It must fail. If it passes, change a byte that is not already zero and verify again.
4. Start the installer and reach **Checking the install media**. It must either re-fetch and repair the path,
   or stop before partitioning and identify damaged install media. The failure details must include the store
   path and must not call this an installer-config hash mismatch or a changed pinned download.
5. Save `/tmp/abora-install.log` and record whether repair succeeded. If continuing the install, first confirm
   `nix-store --verify-path "$victim_path"` passes.

To abandon the experiment, reboot the VM. For an in-session cleanup, unmount the bind mount before deleting
the temporary copy:

```sh
umount "$victim_path"
rm -rf -- "$work_dir"
```

## Boot-menu description

After the successful update, capture `bootctl list` (systemd-boot) or the generated Limine configuration. It is
acceptable for the description line to contain the followed NixOS release name because nixpkgs derives that
read-only text. `/etc/os-release` and `/etc/lsb-release` must still identify Abora OS v4.2 Solstice. Record the
observed description as a known limit, not a failed boot test.
